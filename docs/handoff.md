# Совместная работа и частые ошибки

## Процесс по этапам

В проект добавлялись только файлы текущего этапа, чтобы исполнитель мог использовать `git add .`. Следующий этап готовился после проверки предыдущего коммита в GitHub. Каждый участник использовал собственное авторство Git.

```powershell
git pull --ff-only
# Добавить файлы только своего текущего этапа в корень signal.
git status
git add .
git diff --cached --stat
git commit -m "описание текущего этапа"
git push origin HEAD
```

Не создавайте отдельную вложенную папку проекта при распаковке. Если в архиве есть `src`, `scripts`, `tests` или `supabase`, эти папки должны оказаться прямо в `signal/`. После чужого push остальные участники обновляют чистые рабочие копии через `git pull --ff-only`.

В новом клоне настройте локальные `git config user.name` и `git config user.email` на своё имя и подтверждённый email GitHub. Имя автора и аккаунт, которым выполнен push, — разные настройки. Не подставляйте другого участника в авторство.

Если Git сообщает о конфликтующих локальных файлах, сначала сохраните и сравните изменения. Не используйте `reset --hard` для обхода проблемы. В рабочем дереве не должно быть файлов будущих этапов.

## Node.js и запуск

При `EBADENGINE` и версии Node.js 20 обновите Node.js до 24. Полностью перезапустите VS Code и проверьте `node -v`. Затем повторите `npm ci` и `npm test`.

Если возник `ERR_MODULE_NOT_FOUND` с путём `src/src/server/app.js`, тесты распакованы не туда. Правильно: `signal/tests/app.test.js`. Перенесите ошибочную папку `signal/src/tests` в корень, предварительно убедившись, что не перезаписываете существующие тесты. Импорты в корректном тестовом файле менять не нужно.

Если `.env` отсутствует, выполните из корня проекта:

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
```

Для демо установите `DEMO_MODE=true`. Для реального режима заполните ключи по README. Не отправляйте `.env` в репозиторий.

Если порт 3000 занят, остановите свой предыдущий сервер через Ctrl+C либо выберите другой `PORT` в `.env`. Не завершайте неизвестные процессы.

## Проверка перед защитой

1. `npm ci`, затем `npm test` — ожидаются 7 успешных проверок.
2. `npm start` и http://localhost:3000.
3. Создать рекомендации, сохранить проект, открыть из списка и удалить.
4. Выполнить поиск каналов и ниш. Обозначить учебные примеры, если включён деморежим.
5. Для подключённого Supabase выполнить `database-checks.md` с двумя тестовыми пользователями.

Миграции и инструкция проверки не являются доказательством того, что удалённая БД уже настроена. Результат реальной проверки команда фиксирует отдельно.
