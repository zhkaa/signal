# Проверка облачной базы

Локальные тесты используют изолированный HTTP-сервис. Проверки ниже выполняются после миграций 01–06 в отдельном тестовом проекте Supabase.

1. Зарегистрируйте пользователей A и B, подтвердите почту; проверьте profiles.
2. A создаёт проект. После перезагрузки сессия сохраняется и проект остаётся.
3. B в другом браузере не видит проект A; удаление чужого ID возвращает 404 и не меняет базу.
4. С JWT пользователя B через Supabase API попробуйте вставить проект с user_id=A или изменить владельца собственного проекта на A: RLS должен отказать.
5. Без JWT profiles/projects закрыты; app_settings доступны на чтение, но не запись.
6. user_roles нельзя читать или изменять через publishable key; роль не должна зависеть от user_metadata.
7. Владелец проекта назначает роль admin специально созданному тестовому аккаунту. Только этот аккаунт видит admin overview и меняет объявление; событие записывается в admin_events.
8. Из двух admin-сессий откройте объявление и сохраните разные версии: второе сохранение со старой version получает 409; исходный текст не перезаписывается.
9. После выхода /api/auth/me возвращает 401 и cookie очищены.
10. Проверьте Google после включения provider и URL configuration; отказ/отмена должен возвращать в login с ошибкой.
11. Смена пароля через recovery выполняется в браузере начала запроса и завершается выходом.

SQL Editor и secret/service-role обходят RLS, поэтому они не подходят для проверки доступа обычного пользователя. Не удаляйте реальные учётные записи ради теста. Фиксируйте фактические результаты; успешно выполненная SQL-миграция сама по себе не доказывает все политики.
