# Проверка Supabase перед демонстрацией

Реальная БД не проверяется тестами деморежима. Выполните это в отдельном тестовом проекте после миграций 01–05.

1. Зарегистрируйте пользователей A и B через интерфейс Signal с DEMO_MODE=false. Подтвердите email. Проверьте наличие профилей в Dashboard.
2. A создаёт проект. Перезагрузите страницу, войдите снова: проект остаётся в списке.
3. B в другом браузере не видит проект A. Запрос удаления по ID проекта A не должен удалить его (PostgREST может вернуть успех с нулём затронутых строк).
4. Используя Supabase API и JWT пользователя B, попробуйте вставить проект с user_id пользователя A: ожидается отказ RLS. Попробуйте поменять владельца существующего проекта B на A: также отказ.
5. Без JWT доступ к profiles/projects должен быть закрыт. Для проверки используйте anon key, а не SQL Editor или service-role, которые могут обходить RLS.
6. Попробуйте вставить неверный kind, title короче 3 символов, content без обязательных полей и content более 16 KB: ожидается ошибка ограничения.
7. Обновите проект своим JWT через API Supabase: updated_at должен измениться; проверьте сортировку по created_at и индекс projects_user_created_idx.
8. Удалите тестового пользователя через Supabase Dashboard: связанные профили и проекты должны удалиться каскадно. Делайте это только для специально созданных тестовых аккаунтов.

Не сохраняйте JWT, пароли и ключи в скриншотах и репозитории. Зафиксируйте результат проверки в отчёте команды. Пока реальные ключи не предоставлены, интеграция с Supabase и YouTube требует такой проверки отдельно.
